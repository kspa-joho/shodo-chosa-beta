JZIP連携仕様書

対象アプリ: AppA（被災状況調査アプリ 現場用）／ AppB（被災状況調査アプリ 統合管理版）
Last Updated: AppA Phase 6.25 / AppB Phase 13.35（AppB側は前回記載のまま。AppBスレッドで現在のPhaseへ更新すること）
管理方針: このファイルはbuild.jsには組み込まない。AppAスレッド・AppBスレッドの両方に毎回渡すことで、両アプリの連携仕様を同期させる共通ドキュメント。

⚠️ フィールド追加・変更時のルール： AppAとAppBのどちらかがJZIPのフィールドを追加・変更する場合は、必ず両アプリを同時に修正すること。片方だけ変更すると読み込みエラーや情報欠損が発生する。

1. JZIPファイル構造の概要

JZIPはJSONデータと写真画像をZIP圧縮した独自形式。拡張子は.zip。

ZIP内ファイル構成

パス内容
survey_data.json調査データ本体（フォーム全項目＋位置情報＋photoList）
photos/photo_0.jpg写真ファイル（0始まりの連番）。ただし写真本体がAppA端末内に無い場合は出力されない（3章の注記参照）。
photos/photo_1.jpg写真ファイル（以降同様）

出力ファイル名

AppAの管理タブ「設定」で指定した「出力ファイル名構成」（5項目まで。既定は「調査日」「災害番号」）に従い、調査日・会社ID・班長・整理番号・災害番号の組み合わせで生成される。値中のハイフンは除去され、値が空の項目には文字列nullが入る（例：20260926_null.zip）。全項目が「なし」の場合はsurvey.zip。例：20260615_A001_B001.zip

一括ZIP（AppA Phase 6.17〜）

AppAは複数の現場をまとめて出力できる。管理タブ「設定」の「複数JZIP出力時、まとめて1つのZIPにする」がON（既定）のときは、次の形の外側ZIPを1つ出力する。OFFのときは、現場ごとに上記の単体ZIPを連続でダウンロードする。

パス内容
survey_sites_YYYY-MM-DD.zip外側ZIP（ファイル名）
<ファイル名構成>_<siteId>/survey_data.json現場ごとのフォルダ。例：20260926_D001_2026-09-26-001/。中身は単体ZIPと同じ。
<ファイル名構成>_<siteId>/photos/photo_N.jpgその現場の写真
⚠️ 未確認事項（AppB）：AppBの読込処理が一括ZIP（ZIP直下ではなく現場ごとのフォルダにsurvey_data.jsonがある形）に対応しているかは未確認。なお、AppA自身の「JZIP読込」は単体ZIP（survey_data.jsonがZIP直下）専用で、一括ZIPは読み込めない。
siteIdはAppA端末内の連番（日付＋連番）であり、業務上の識別子は整理番号（ref_no）。AppBでsiteIdを識別子として使わないこと。

2. survey_data.json フィールド定義

mainGeom・subGeom・photoList 以外のフィールドはすべてHTMLフォームのname属性から直接収集される。

2.1 管理項目

キー名型必須説明
company_idstring必須会社ID。ファイル名構成にも使用。
leader_namestring必須調査班長名。
ref_nostring必須整理番号。AppBでの一意管理キーの一部。
survey_datestring (YYYY-MM-DD)必須調査日。
disaster_nostring必須災害番号。

2.2 諸元

キー名型必須説明
dept_namestring任意所属名（発注者名）。
loc_namestring任意被災場所（住所等）。
route_namestring任意路線・河川名等。

2.3 被災状況

キー名型必須説明
damage_datestring (YYYY-MM-DD)任意被災日。
lengthstring (数値)任意延長 [m]。
heightstring (数値)任意高さ [m]。
side_typestring任意岸別。値：「右岸」「左岸」「距離標なし」「none」。
distance_labelstring任意距離標・区間。例：「4k000」。
commentstring任意コメント。

2.4 被災拡大の可能性

キー名型必須説明
expansion_existsstring任意有無。値：「有」「無」「none」。
expansion_statusstring任意拡大状況の説明。

2.5 特記事項

キー名型必須説明
special_existsstring任意有無。値：「有」「無」「none」。
special_statusstring任意特記状況の説明。
plan_summarystring任意対策の概要。

2.6 調査を実施した者

キー名型必須説明
company_namestring任意会社名。
telstring任意電話番号。
faxstring任意FAX番号。
person_namestring任意職氏名。
emailstring任意E-mail。

2.7 位置情報（GeoJSON）

キー名型必須説明
mainGeomGeoJSON FeatureCollection任意メイン図形（赤）。ポイント/ライン。AppBが地図に表示する。AppAのメイン図形は常に最大1件（新しく描くと既存のメインは置き換わる）。ポイントは位置を示すマーク（〇）の座標1点で、大きさ等の表示情報はGeoJSONに含まれない（AppAが画面上で固定サイズのマークとして描く。表示の仕様はAppAの実装の詳細でありJZIPの内容ではない）。座標は[経度, 緯度]の順（GeoJSON標準）。
subGeomGeoJSON FeatureCollection任意サブ図形（青）。落書き・テキスト注釈。
mainGeomのfeatures[0].geometryからAppBが座標を自動抽出し、start_lat/start_lng/end_lat/end_lngに格納する（AppB側の処理）。

2.8 写真リスト

photoListは配列。各要素の定義は次節参照。

3. photoList フィールド定義

キー名型必須説明追加Phase
fileNamestring必須 写真のファイル名。AppA（Phase 6.23時点）が実際に出力する値はphoto_0.jpgの形で、photos/は含まない。ZIP内の実際の位置はphotos/フォルダの下（photos/photo_0.jpg）。AppAの読込はphotos/を付け足して取得している。
※旧版の記載（photos/を含むパス）とは異なる。AppB側がどちらの形を前提に読んでいるかは未確認。		 初期
memostring任意 写真の備考。空文字の場合あり。 初期
tagstring必須 写真タグ。値：「全景」「近景」「補足」「地図メモ」。ソート順：全景→近景→補足→地図メモ。 初期
azimuthnumber / null任意 撮影方向（度・0〜359）。null=未記録。0は真北を意味する有効値であり、nullとは別物。 AppA 5.44
latnumber / null任意 写真GPS緯度。null=未取得。撮影時自動記録またはEXIF読み込みまたは地図タップ修正による値。 AppA 5.44
lngnumber / null任意 写真GPS経度。null=未取得。latと同様。 AppA 5.44
gpsAccuracynumber / null任意 GPS精度（メートル）。null=精度不明（EXIFから読んだ場合・地図タップ修正後も含む）。数値=撮影時のwatchPositionによる実測精度。 AppA 5.44
gpsFixedboolean任意 地図タップ修正済みフラグ。true=ユーザーが地図をタップして位置を手動修正済み。falseまたは未定義=通常。 AppA 5.51
photoListと実ファイルの不一致（AppA Phase 6.17〜）： AppAは、写真本体（端末内のIndexedDB）が見つからない写真について、photoListの要素は出力するが、対応するphotos/photo_N.jpgのファイルは出力しない。したがってphotoListにあるのに実ファイルが無い、という状態が起こり得る。AppBは実ファイルが無い写真を許容して読み込むこと（例：その写真をスキップする。エラーで止めない）。
写真のEXIF情報について： AppAはJZIPエクスポート時に piexifjs を使って各JPEGに GPSLatitude/GPSLongitude/GPSImgDirection を書き込む。 ただしリサイズ処理でEXIFが消えるため、エクスポート時に書き直す方式をとっている。 AppBはJPEGのEXIFを直接読まず、survey_data.jsonのphotoListから位置・方位情報を取得すること。

5. フィールド追加時のルール

ルール1：両アプリ同時修正の原則
photoListまたはsurvey_data.jsonにフィールドを追加・変更する場合は、AppAとAppBを同じタイミングで修正する。片方だけ先行して変更しない。
ルール2：後方互換の確保
新フィールドは必ず任意（optional）とし、未定義・nullの場合のデフォルト動作を両アプリに実装すること。既存JZIPファイルが読み込めなくなる変更は禁止。
ルール3：本ファイルへの記録
フィールドを追加した場合は、本ファイル（jzip_spec.html）のフィールド定義表と変更履歴を必ず更新する。更新時はAppAとAppBのPhase番号を両方記載する。
ルール4：型の厳守
数値フィールド（azimuth/lat/lng/gpsAccuracy）に文字列を入れない。null許容フィールドにundefinedを使わない（必ずnullを使う）。
