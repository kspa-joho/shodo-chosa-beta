1. プロジェクト背景と目的

大規模災害時、通信遮断下にある現場から、確実に被害状況を事務所へ届けるための建設コンサルタント専用ツール。鹿児島県測量設計業協会の情報専門部会が主導して開発。

  • Local-First: サーバー・DB不要。PWAとしてスマホにインストールして動作する。
  • Bucket Relay: データ連携は物理的なファイル移動（JZIP形式）で行う。
  • Offline First: Service Workerにより地図タイル含めオフライン動作を保証する。

2. 開発運用ルール（SSOT）

  • Phase管理: 会議の局面管理番号（X.XX）。package.jsonのversionおよびconfig.phaseを正とする。
  • 永遠のβ版: 現場フィードバックにより開発は永続する。「完成」と決めつけない。
  • Spec as Code: 本ファイル（src/spec.html）はプロジェクトの唯一の正解情報（SSOT）である。
  • コード提示ルール: 省略不可・全文表示・変更ファイルのみ・圧縮不可。最適化と意匠変更は判断を仰ぐ。毎回 package.json と spec.html を提示する。

5.2 写真機能

  • 写真エリアのUI配置順（確定）: ナビゲーション → プレビュー → タグ・削除 → 📷撮影・📁ファイル選択ボタン → 写真の備考 → センサーエリア（撮影方向・位置情報）
  • カメラinput分離（確定・変更禁止）: photo-camera-input（handleCameraFile・GPS自動記録）/ photo-file-input（handleFileSelect・EXIF読み込み）。changeリスナーはDOMContentLoaded内でaddEventListenerで登録（iOS対応）。
  • IndexedDB永続化（photoStorage）: 撮影・選択・削除・ソート・並び替え時にsyncAll()。アプリ起動時にrestore()でdataUrlを復元。アプリが落ちても写真が消えない。
  • 4:3強制クロップ: 縦を基準に左寄せで右側をカット。targetWは4:3後の横幅が基準。管理タブのチェックボックスで制御。
  • 撮影ボタンのGPS表示: 「誤差○m」を直接表示。未取得時は点滅。GPS起動はDOMContentLoadedで実施。
  • 位置情報4状態: ○m（精度あり）/ 修正済み（地図タップ後・青・座標表示）/ 不明（EXIFから）/ 未取得
  • GPS修正フロー: 修正ボタン→写真タブ閉じ→位置図タブ開く（現在ズーム+2）→地図タップ→写真タブに戻る。gpsFixed=true。
  • 方位センサー優先順位: webkitCompassHeading（iOS・真北基準）→ deviceorientationabsolute（Android等・真北基準）→ deviceorientation（フォールバック）
  • 撮影方向は記録/削除ボタン方式のまま（GPSのみ修正ボタンに一本化）。
  • JZIPエクスポート時のEXIF書き込み: piexifjsで既存EXIFにマージしてGPS座標・方位・精度を書き込む。エラー時フォールバック。
  • リサイズ横幅指定: 管理タブで800/1200/1600/2000px・なしを選択。デフォルト1200px。

5.3 地図機能

  • ポリライン描画の完了はボタン専用（マーカータップ無効）。
  • モード：メイン(位置)・サブ(落書き)・白紙メモの3モード。モード切替ボタンはCSS activeクラスで色制御（インラインstyle禁止）。
  • maxZoom:25（オーバーズーム対応）: maxNativeZoom:18（地理院）/19（ESRI）でタイルを拡大表示。
  • 地図初期化タイミング（確定・変更禁止）: storageManager.load()では初期化せず、アコーディオンを開いたときにinvalidateSize()→ペンディングデータ復元の順で実行。DOMサイズ0での初期化を防ぐ。
  • 地図キャッシュ: 表示したタイルを自動でCache Storageに蓄積（Stale-While-Revalidate方式）。管理タブに「地図キャッシュを開放する」ボタンあり（LocalStorageには影響しない）。

5.4 初期値・クリア機能

  • 保存内容: 会社情報（company_id/leader_name/company_name/tel/fax/person_name/email）・fn1〜fn5・photo_resize_width・photo_force_43
  • 保存先: LocalStorage（キー: survey_app_defaults）。起動時にloadDefaults()で自動読み込み。
  • クリア（初期値を残す）: フォーム・写真・地図・白紙メモ・オートセーブ・IndexedDBを全消去→初期値を適用。確認ダイアログあり。
  • クリア（全未入力）: 同上だが初期値を適用しない。確認ダイアログあり。
  • 初期値の読み込み: 入力内容はそのまま・初期値フィールドだけ上書き。
  • 初期値のLocalStorageはクリア操作では削除しない。

5.8 地図を写真に保存：自前タイル転写方式への変更（Phase 6.05・Step2-①解決）

  • 不具合の内容: 位置図を拡大して「地図を写真に保存」すると、真っ黒な画像として保存される場合があった。実機確認：ズーム18は正常、ズーム19から真っ黒（地理院標準・地理院写真とも同じ境目）。
  • 検討した経緯（3案）:
    • ①leaflet-image（旧方式）：タイル画像をサーバーへ再取得して合成する方式のため、地理院タイルのmaxNativeZoom(18)を超えるオーバーズーム状態（Leafletが18のタイルを画面上で引き伸ばして見せているだけで、実タイルが存在しないズームレベル）では、その場に無いタイルの再取得に失敗し、失敗箇所が透明のまま残る。JPEG変換時に透明部分が黒く塗りつぶされていた。
    • ②html2canvas（Phase 6.05で一時採用→撤回）：画面全体をキャプチャする汎用ライブラリ。内部でクロスオリジン画像を安全に読めるか検証するために画像を読み直す挙動があり、地理院タイルサーバー側でエラー（404）になり、同じく黒くなることを実機で確認。地理院タイルサーバーとの相性が悪く採用を見送った。
    • ③自前タイル転写方式（採用）：①②はどちらも「タイル画像をもう一度サーバーから取り直す」ことが失敗の根本原因だったため、新規の通信を一切せず、画面に既に読み込み済み・表示済みのタイル<img>要素をそのままcanvasへ描き写す方式に変更した。
  • 実装内容:
    • タイル：#map内の.leaflet-tile-pane配下、読み込み済み（img.complete）の<img class="leaflet-tile">要素を、その要素自身のgetBoundingClientRect()に基づく位置・サイズでcanvasへdrawImage()する。
    • メイン(赤)・サブ(青)の図形：allDrawnItemsの緯度経度情報から、map.latLngToContainerPointで自前に座標変換して描き直す（円・ポリライン・ポリゴンに対応）。円の半径(メートル)は、中心から実距離ぶん東へ移動した地点を同じ座標系に投影して画面上のpx半径を算出する（外部プラグイン不要）。
    • 注記（テキスト）：従来通り、位置を計算してcanvas上に吹き出し風のボックスとして手描きする。
    • サブレイヤー除外ロジックは維持：メインモードで保存する際はcurrentMode==='main'かつisMain===falseの図形を対象から除く、という既存ルールをそのまま踏襲。
    • Leafletコントロール（ズームボタン・ズームレベル数値・レイヤー切替・描画ツールバー等）はそもそも合成対象に含めていないため、隠す処理自体が不要になった（＝確実に写り込まない）。
  • 仕様として確定した挙動: 19以上に拡大した状態で保存すると、地理院タイルの実解像度（18相当）を超えて引き伸ばされた粗い見た目が、その粗さのまま保存される。図形・線・文字はピクセルサイズを維持したまま正確な位置に描画されるため、大きさが不自然に変わることはない。粗いかどうかはユーザー自身が画面を見て判断し、必要なら少しズームを戻してから保存する。アプリ側で18に自動的に戻す・19以上の保存を禁止する、といった制御は行わない。
  • 既知の簡略化: サブ(落書き)モードで置いた素のマーカー（旗揚げ用途）は、Leafletの標準ピン画像そのものではなく、色付きの丸として簡略描画する。
  • 依存ライブラリの削除: leaflet-image・html2canvasのいずれもindex.html.templateから削除した。地図画像化は外部ライブラリ非依存になった。
  • 地理院地図Vector（ベクトルタイル）は今回の対応範囲外: Vector化すれば地理院標準は理論上どのズームでも実データを描き直せるが、地理院写真（航空写真）・ESRI衛星は実写真のタイル画像であるためVector化できず、同じ問題が残る。今後の検討課題として残す（実装は別スレッドで大きめの改修になる想定）。

5.10 位置図の縦横比を4:3に固定（Phase 6.05・Step2-②解決）

  • 不具合の内容: 位置図（#map）の画面表示が画面の高さに対する割合（55vh）で決まっていたため、帳票側の位置図の枠と縦横比が一致せず、帳票にフルサイズで収まらなかった。
  • 検討の経緯: 当初はExcel帳票の位置図セルの実測値（幅12.86cm×高さ6.64cm、約1.94:1）に合わせる案で検討したが、この比率は横に長すぎてスマホでの地図操作が窮屈になる懸念があった。写真（全景・近景等）は4:3で統一されていることもあり、位置図も4:3で統一する方針に変更。帳票側のセルサイズはAppB側で4:3に合わせて調整する（AppBスレッドで対応、本スレッドの対応範囲外）。
  • 採用しなかった案：
    • 保存時だけズームを戻して撮る案：描画済みの線・文字がピクセル固定サイズのため、縮小すると地図に対して相対的に大きく・太く見えてしまい却下。
    • 保存時だけ帳票比率のCanvasを作り黒縁で埋める案：画面に見えている地図と保存される画像の縦横比が食い違ってしまうため却下（Phase 5.97で確立した「画面と保存物を一致させる」方針に反するため）。
    • 地図の上に保存範囲の枠線を重ねて表示する案：画面と保存物は一致するが、地図の表示エリア自体の操作性は変わらないままにできる一方、枠の管理が二重構造になるため、そもそも表示エリア自体を4:3にする方が単純と判断。
  • 実装内容: #map-containerの幅にmax-width: min(100%, 93.333vh)を設定し、その中の#mapをwidth:100%; aspect-ratio:4/3で表示する。93.333vhは「高さの上限70vh」から逆算した値（70vh×4/3）。画面幅が十分に狭ければ100%幅が優先されて4:3のまま伸縮し、フルスクリーン等で幅が広がりすぎる場合はmax-widthが効いて高さが70vhを超えないよう自動的に絞られる。
  • 画面と保存画像は一致したまま: 表示エリア自体の縦横比を変えただけなので、「地図を写真に保存」（5.8参照）の実装や、画面に見えている通りに保存されるという原則には変更がない。
  • 白紙メモ（#sketch-container）は対象外: 帳票の位置図枠とは無関係の自由記述キャンバスのため、従来通り window.innerHeight*0.55 ベースのサイズのまま変更していない。

5.9.1 白紙メモのツールボタンとモードタブのクラス名衝突を修正（Phase 6.05）

  • 不具合の内容: 白紙メモでペン・消しゴム等のツールを選ぶと、位置図の「白紙メモ」モードタブの色（active時の青）が消えて黒くなっていた。
  • 原因: 白紙メモのツールバー内ボタン（ペン・直線・文字・消しゴム）と、メイン/サブ/白紙メモのモード切替タブ（mode-btn-map等）が、どちらも共通のCSSクラス名sketch-btnを使っていた。sketchApp.setTool()がdocument.querySelectorAll('.sketch-btn')でページ全体からactiveクラスを一括除去していたため、ツール選択のたびにモードタブのactive状態まで巻き込まれて消えていた。
  • 対応: setTool()の対象を.sketch-toolbar .sketch-btn（白紙メモのツールバー内のみ）に限定した。

5.12 白紙メモのベクタ化 段階1（Phase 6.05・Step2-③着手）

  • 設計方針: ペン・直線・文字を、Canvasへ直接ピクセルを塗るのではなく、sketchApp.elements配列に要素として個別に保持する方式に変更した。
    • ストローク要素: { type:'stroke', mode:'free'|'line'|'eraser', color, points:[{x,y},...] }
    • テキスト要素: { type:'text', x, y, color, text }
  • 再描画方式: 操作のたびにredrawAll()でCanvasを白背景で塗り直し、elements配列を先頭から順に描き直す。描画中のストロークはelementsに入れず、プレビューとしてredrawAll()の後に重ねて描く。
  • undo: elements配列の末尾を1件popして再描画するだけ。従来のようにCanvas全体の画像（history配列・toDataURL）を保存・復元する仕組みは廃止した。
  • 全消去: elements配列を空にして再描画するだけ。
  • キャンバスを4:3に固定（Step2-②と統一）: .sketch-canvas-containerに位置図と同じmax-width: min(100%, 93.333vh) + aspect-ratio: 4/3を設定。JS側resizeAndClear()もcanvas.height = canvas.width*3/4で同じ比率にする。リサイズ時にelementsは保持したまま再描画するため、従来のように白紙メモの内容がリサイズで消えることもなくなった。
  • 今回は含めない（段階2以降）: 文字要素の移動・回転・複数行入力、拡大(ズーム)した状態での記入、ブラウザバック対策。elements配列という土台ができたため、これらは同じ土台の上に追加していく形で対応する。

5.13 白紙メモのベクタ化 段階2（Phase 6.05）

  • 文字要素に持たせたデータを拡張: { type:'text', x, y, color, text, rotation }。rotationはラジアン、初期値0。textは改行\nを含む複数行に対応。
  • 選択・移動: 白紙メモモードで既存の文字をタップすると選択され（新規作成にはならない）、そのままドラッグで移動できる。何もない場所をタップした場合のみ新規文字入力になる。
  • 当たり判定（hitTestText）: タップ位置を要素の回転角の逆回転で戻してから、未回転のバウンディングボックス（getTextBounds）と比較することで、回転させた文字に対しても正しく選択できるようにしている。
  • 回転: 選択中に浮動ツールバー（↺/↻）で±15度ずつ調整する。指でつまんで回す操作は行わない（実装の複雑さを避けるため）。
  • 複数行入力: 従来のwindow.prompt()（1行しか入力できない）を廃止し、textareaを持つ専用モーダル（#sketch-text-modal）に変更した。新規入力・既存文字の編集（✏️ボタン）の両方で共通利用する。
  • 削除: 選択中の浮動ツールバーの🗑ボタンで、その文字要素だけを削除できる（undoを使わずピンポイントで消せる）。
  • 選択枠・浮動ツールバーは保存前に解除: saveToPhoto()実行時に選択を解除してから描き直すため、青い点線の選択枠やツールバーが保存画像に写り込むことはない。

5.14 白紙メモ：消しゴム廃止・編集モードへの統合（Phase 6.05）

  • ツール構成の変更: ペン(free)・直線(line)・文字(text)・編集(edit)の4つに変更。消しゴム(eraser)は廃止した。
  • 編集モードでの選択・操作:
    • 文字：タップで選択→ドラッグで移動。浮動ツールバーで回転(±15度)・内容編集(✏️)・削除(🗑)。
    • 直線：始点・終点それぞれに丸いつまみ(半径14px判定)を表示し、個別に位置を直せる。つまみ以外の線上(線分までの距離12px以内)をつまむと線全体を平行移動できる。浮動ツールバーは削除のみ。
    • ペンの線：バウンディングボックス(余白15px)内のタップで選択し、そのまま平行移動する。形は変えない・拡大縮小もしない。浮動ツールバーは削除のみ。
  • 消しゴム廃止の理由: 個々の要素を選んで🗑で消せるようになったため、面で塗りつぶして隠す方式の消しゴムは不要と判断し廃止した。
  • 移動の実装: ドラッグ中は直前の位置との差分(dx, dy)を毎回加算していく増分方式。文字はx,y、直線・ペンは全ての点に同じ差分を加える。
  • 選択中の見た目: 文字・ペンの線は点線の枠、直線は始点・終点に半透明の丸いつまみを表示する。保存前(saveToPhoto())には選択を解除して描き直すため、これらの表示は保存画像に写り込まない。

5.15 「線」ツールを連続線（折れ線）に変更（Phase 6.05）

  • 変更前: 「直線」ツールは始点・終点の2点だけを持つ直線だった。
  • 変更後: タップするたびに頂点を1つずつ追加していく連続線（折れ線）に変更。ボタン名も「直線」→「線」に変更した。
  • 作図の操作: タップ＝1点追加（ドラッグ中の移動は見ない。タップした瞬間の位置だけを見る）。「線」モードの間だけ右上に「完了」「中止」ボタンが浮動表示される。完了で2点以上あれば要素として確定、中止で描きかけの内容を破棄する。他のツールに切り替えた場合も、描きかけの連続線は自動的に破棄する。
  • 編集モードでの操作: 確定した連続線は、途中の頂点も含めた全ての点につまみ（半径14px判定）を表示し、どの頂点も個別にドラッグして直せる。つまみ以外の線上（各線分までの距離のうち最小値が12px以内）をつまむと線全体を平行移動する。
  • データ構造: pointsが2点固定ではなく可変長になった。drawStroke()も先頭・末尾の2点だけを見る特別扱いをやめ、全ての点を順になぞって描く（ペンと同じロジックに統一）。

5.16 線の頂点単体削除・作図中の点の可視化（Phase 6.05）

  • 頂点1点だけの削除: 編集モードで線の頂点のつまみを選ぶと、選択した頂点の情報をselectedPointIndexとして保持する（要素全体の選択selectedIndexとは別に管理）。浮動ツールバーに「この点だけ削除」ボタン（✂️）が現れ、線全体ではなく、つまんだ頂点だけを削除できる。頂点が2つしかない線では表示しない（それ以上減らすと線として成立しないため、その場合は🗑で線ごと削除する）。
  • 作図中の点の可視化: 「線」モードでタップして頂点を追加していく間、置いた各点に小さい丸印（要素の色で塗りつぶし、白い縁取り）を表示するようにした。1点目を置いた直後は線がまだ引かれていない（点が1つしかないため）ため見えづらかったが、この丸印により1点目の位置も確認しながら2点目以降を打てるようになった。確定後の線には丸印は表示されない（作図中のみのプレビュー）。

5.17 段階3（拡大して細部記入）は見送り（Phase 6.06判断）

  • 見送りの理由: 白紙メモは地図や写真のような下地画像の上に描くものではなく、真っ白な紙に描くだけのものである。地図の拡大とは違い、「実際の地形を見て正確な位置を確認したい」という強い理由が存在しない。
  • 元の要望「拡大して細部を記入したい」は、段階1〜2で編集（あとから位置を選んで直せる）ができなかった時代に、「最初から正確に描くしかない」という制約から来ていたと考えられる。段階2までの対応（文字・線の選択移動、頂点単体の位置調整）により、大まかに描いてから後で位置を整える、という形でこのニーズには実質的に応えられていると判断した。
  • あわせて、フルスクリーン(⛶)ボタンにより画面自体を大きくして描く選択肢も既にある（Step2-②で4:3固定にした際にも維持済み）。
  • ズームしながら描く仕組み自体（1本指=描画/2本指=ピンチズームの共存）は、実装コストの割に誤操作のリスクが大きいため見送る。将来、白紙メモに下地画像を貼る機能等が追加され、下地を細かく見る必要が生じた場合は、改めて検討する。

5.18 ブラウザバック対策（Phase 6.07・Step2-③段階4）

  • 不具合の内容: 端末・ブラウザの「戻る」操作（ジェスチャー・戻るボタン）で意図せず離脱すると、ページごとリロードされ、白紙メモを含む入力中のデータが全て失われる。
  • 対応方針: 改修指示書で挙げられた2案（確認ダイアログを出す／history操作を制御して離脱を抑止する）のうち、後者を採用した。確認ダイアログはうっかり誤タップで進んでしまうリスクが残るため、より確実な抑止方式を選んだ。
  • 実装: アプリ起動時にhistory.pushState()でダミーの履歴を1つ積んでおく。popstateイベント（戻る操作）が発生するたびに、再度ダミー履歴を積み直すことで、実質的にページ離脱そのものを防止する。戻るたびにトースト通知（「入力中のデータを守るため、戻る操作は無効にしています」）を出す。
  • 影響範囲: 白紙メモに限らず、管理項目・諸元・写真等すべての入力データが対象になる（データ保護の仕組みとしてアプリ全体にかかるため）。
  • SW更新・更新確認との切り分け: checkForUpdate()やSW更新時のlocation.reload()はプログラムによる明示的な画面遷移であり、popstate（戻る操作）とは別物のため、この対策の影響を受けず従来通り動作する。

5.19 撮影方向欄に8方位のライブ表示（Phase 6.08・Step2-⑤着手）

  • 経緯: 改修指示書Step2-⑤（GPS・方位取得のUI調整）のうち「使い方が不明」「8方位程度で手入力できる代替手段」に対応する。撮影方向欄は元々数値の手入力ができたため、8方位ボタンを新設するのではなく、数値を入力した際にその場で8方位の文字（北・北東・東・南東・南・南西・西・北西）を表示するだけの、既存スペースを使った軽い対応とした。
  • 実装: photoApp.updateAzimuth()（撮影方向inputのoninput）で、既存の#photo-azimuth-dir枠に8方位の文字をその場で反映するようにした。従来は写真を切り替えたとき（renderAzimuthField）にしか反映されず、入力中は空欄のままだった。
  • 8方位・16方位の使い分け: 新設したphotoApp._dir8()は8方位専用。既存のazimuthManager._dir()（16方位：北北東等）は、現在の方位のライブ表示・記録時のトースト通知など、別の場所でそのまま使い続ける。同じ#photo-azimuth-dir枠は、入力中・写真切替時のどちらもphotoApp._dir8()（8方位）に統一し、表示形式が場面によって16方位⇔8方位に切り替わって紛らわしくなることを防いだ。
  • 残り（Step2-⑤の他の項目）: GPSは搭載端末推奨の案内表示、方位が任意機能である旨の明記は未着手。

5.20 GPS・方位の使い方説明を追加（Phase 6.09・Step2-⑤解決）

  • 対応内容: 改修指示書Step2-⑤の残り2点（GPSは搭載端末の使用を推奨する案内、方位は必須ではない旨の明記）に対応した。

  • 部品ファイルの差し替え漏れに注意: src配下のファイルは互いにバージョンがずれると症状の切り分けが難しくなる。改修のたびに影響する全ファイルを一式で提示・反映する。
  • 地図の画像化は「タイルを再取得しない」方式で確定（Phase 6.05）: leaflet-image・html2canvasはいずれも地理院タイルサーバーとの相性問題（オーバーズーム時の404・CORS絡みの再取得失敗）で真っ黒画像を引き起こした。既に画面へ読み込み済みのDOM要素（<img>タイル）をそのまま転写する自前実装に統一し、新規のタイル取得を一切発生させない方針とする。今後、地図の画像化まわりを触る際もこの方針を踏襲する。

7.1 管理項目の参照ボタン（設計確定・⑥と同時実装）

同一災害で複数現場を回る際、共通する管理項目を他の現場から引き継ぐための機能。⑥で現場データの持ち方が変わるため、⑥の実装時に合わせて作る（先行実装すると二度手間になるため）。

  • 配置: 管理タブ「管理項目」アコーディオン内に参照ボタンを置く。
  • 選択肢（4択）:
    • ①指定した初期値を引用（「初期値として保存」で保存した値）
    • ②最後の現場を参照
    • ③それ以外の現場を指定して参照（⑥の現場リストから選択）
    • ④キャンセル
  • 引き継ぐ項目: 災害番号・発注者名・被災日・整理番号の4項目。
  • 整理番号の扱い（Phase 5.92確定）: 空欄にはせず、参照元の値をそのまま引き継ぐ。ただし現場ごとに異なるはずの項目なので、書き換え忘れに気づけるよう文字色を変えて表示する。
  • 前回値であることを示す文字色表示: 参照で引き継いだ災害番号・発注者名・被災日・整理番号の4項目は、引き継ぎ直後は目立つ色（オレンジ等）で表示する。ユーザーがその項目の値を実際に書き換えた時点で通常の文字色（黒）に戻す。フォーカスが入っただけ・クリックしただけでは色は変わらない（値の変更で判定する。inputイベントでのみ色を戻し、focus/blurイベントでは戻さない）。色が前回値のままでもその値は正式な入力値として採用される（未入力・無効という意味ではない）。
  • 調査日： 参照元の日付ではなく今日の日付のままとする（色表示の対象外）。
  • ①の前提: 「初期値として保存」の保存対象（survey_app_defaults）に災害番号・発注者名・被災日を追加する（整理番号は初期値保存の対象外。②③の現場参照でのみ引き継ぐ）。

アプリとしてインストールする方法

このツールは、ホーム画面に追加することで「アプリ」として動作し、 オフライン起動や全画面表示が可能になります。

iPhone (Safari) の場合

  1. 画面下部（または上部）の 共有ボタン ⎋ をタップします。
  2. メニューをスクロールして 「ホーム画面に追加」 を選択します。
  3. 右上の 「追加」 をタップします。
  4. ホーム画面にアイコンが追加され、次回からそこから起動できます。

Android (Chrome) の場合

  1. 画面右上の メニューボタン ⋮ をタップします。
  2. 「ホーム画面に追加」 または 「アプリをインストール」 を選択します。
  3. 確認画面で 「追加」 をタップします。
  4. ホーム画面にアイコンが追加され、次回からそこから起動できます。
注意: PCでHTMLファイルを直接開いている場合、保存機能などが一部制限されることがあります。 さくらサーバー等のWebサーバーにアップロードしてからご利用ください。
